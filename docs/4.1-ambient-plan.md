## 0. 一页结论

1. **无感入口 = 原生会话页内的「星桥任务条」+ 只在异常/待审批时出现的「注意力气泡」**。不打开星桥独立窗口、不展开右侧栏、不切屏；同时让会话（模型）在每步上下文里看到「本会话此刻的星桥态势」，自然优先用星桥工具解决跨会话问题。
2. **DSH 客户端 slot 能力足够，MVP **零 DSH 宿主改动**。** 相关 slot（`conversation.session.header.utilities/.actions`、`conversation.composer.dock`、`shell.overlay` 等）都由现有客户端 UI 包声明，第三方客户端插件可用 `ctx.slots.inject(key, () => ctx.slots.register({...}, Component))` 注册；星桥 `client.js` 已经在浏览器加载（实测 boot graph 有 `dsh-plugin-session-bridge` 条目，见 §2.1）。
3. **真正需要改的是星桥两侧插件 + 数据面**：
   - 星桥 host 插件 `index.js`：新增 **轻量 ambient 投影 + 端点**（全量 `state` 实测 392 KB，不能给 5s 轮询用）、`inbox.ack`、`approval.approve`（面板直批）、模型侧 ambient 运行上下文块。
   - 星桥 client 插件 `client.js`：注册 3 个 seat（header 任务条、composer dock 条、注意力气泡浮层）+ 共享轮询 store + 内联动作。
4. **内联动作分三条路径**（避免越权/重复实现）：
   - **panel 直执行**：`approval.approve` / `approval.reject` / `inbox.ack` / `task.claim`（已有）→ 适用于“用户本人拍板”的动作；
   - **steer 当前会话**：`session_ask` / `group_recruit` / `task_transfer` / `council_vote` → 由 host 生成结构化指令并 `steer` 进当前会话，复用既有工具逻辑与权限（1 次点击，零切换）；
   - **深链/右侧栏**：只作为二级入口，**不进 MVP 主链路**（违反零切换）。
5. **模型侧「星桥优先」= 静态硬规则（已有，`index.js:227`）+ 每步 ambient 动态块（新增）**。静态规则告诉模型“应该用星桥”，ambient 块告诉它“此刻找谁、做什么、用哪个工具”，二者缺一不可。
6. **4.1 排序**：P0 = ambient 数据面 + `inbox.ack`/`approval.approve` + 模型 ambient 块 + header 任务条/注意力气泡（零 DSH 改动，1–2 周）；P1 = 4 个工具的内联 steer 动作、合成任务线 flow、全局气泡/侧栏角标；P2 = DSH 宿主新增“真·顶部全宽 banner” slot、通知中心/OS 通知、资源排队可视化（需改 DSH 或跨仓库）。
7. **验收新增硬指标**：跨会话问题从原生页发起星桥动作 **≤1 次点击 / 零切换**（定义与单条/多条判定见 §6.2 A4）；并且有 pending 时模型上下文出现 ambient 行、无 pending 时零注入。

## 1. 背景、用户诉求与目标

### 1.1 用户诉求（task-18 原文归纳）

- 不想为了用星桥切屏/刻意打开星桥窗口；希望星桥**无感嵌入 DSH 原生会话页**。
- 产品分层结论（GPT）：**原生会话 = Interaction Layer**（用户/模型正在对话的地方），**星桥 = Orchestration Layer**（跨会话找人/任务/审批/资源）；不应让用户离开会话去找星桥。
- Lead 补充硬要求（本次追加）：4.1 无感入口必须**鼓励会话优先用星桥解决问题**，不只是方便用户看：
  - 会话遇到跨会话问题（找人/进度/交接/转交/审批/资源冲突/查经验）先走星桥；系统提示已加「星桥优先（v4.0）」硬规则；
  - 无感入口要让会话在原生页看到「当前任务/待协作事项/待审批」，并给出 inline 动作（`session_ask`/`group_recruit`/`task_transfer`/`council_vote`），而不是让会话自己开子代理或先问用户；
  - 评估哪些 slot/提示/状态能让会话自然优先走星桥；哪些必须改宿主；
  - 验收加一条：跨会话问题从原生页发起星桥动作的路径 ≤1 次点击/零切换。

### 1.2 4.0 现状与缺口（为什么“右侧栏 tab”仍不无感）

- 4.0 的星桥 UI 是**独立窗口** `app.html` + **右侧栏 tab**（`client.js:5395-5475` 注册 `sidebarRightTabs` 类型、`sidebar.right.pane.tab` 面板体、`sidebar.footer.action` 入口）；右栏**默认折叠**，用户要看待办需：展开右栏 → 找到星桥 tab → 在面板里扫（或打开独立窗口切屏）。这满足“有地方看”，不满足“无感”。
- 用户当前使用中，上一条路径需要**主动操作 ≥2 次 + 离开会话视线**；而跨会话待办最需要的是“在对话发生的地方冒一行/冒一个气泡”。
- 4.0 已具备的数据面（`index.js:3335 stateForUi`）已经覆盖任务线、收件箱、指挥中心、资源快照；缺的是**贴着会话的呈现**和**会话侧的即时态**。

### 1.3 4.1 目标与成功指标

| # | 目标 | 可验收结果 |
|---|---|---|
| G1 | 不离开会话即可看到“我现在的星桥任务/待协作/待审批” | 打开任意会话，header 出现任务条（有任务时）；无任务无占位 |
| G2 | 只有异常/待审批才打扰 | `attentionCount=0` 时零气泡；出现后 1 次点击可处理，处理后消失 |
| G3 | 会话自然优先走星桥 | 构造跨会话场景，模型无用户提示时首选星桥工具；上下文含 ambient 行 |
| G4 | 零切换完成动作 | 单条待办 1 次点击；动作在会话页内闭环，不展开右栏/不开窗口 |
| G5 | 轻量、可降级、不回归 | ambient 端点 <20KB/次；失败隐藏不阻断；4.0 契约测试 ALL PASS |

## 2. DSH 客户端 slot 能力盘点（事实与证据）

### 2.1 客户端插件加载机制（已实测）

- 机制：包在 `package.json` 声明 `dsh.client.platform='web'` 且 `exports['./client']` 指向客户端 bundle；`dsh-client-modules` 的 Node 半侧扫描 Loader 条目、按“行模块的最近 package.json”解析声明，把 bundle 以 `/plugins/<pkg>/client.js&rev=<mtime/size 派生>` 提供给浏览器，并写入 `window.__DSH_BOOT__`（`pkgs-ambient/.../dsh-client-modules/README.zh.md`「声明客户端插件」「惰性 CJS 模型」；解析逻辑 `dsh-client-modules/lib/index.js:728-830`）。
- 关键点：**本地哈希安装（`loaded/index-<hash>.js`）也能被识别到客户端半侧**——解析走“模块 URL 的最近 package.json”，星桥 `loaded/` 的父目录就是 `dsh-plugin/package.json`（含 `dsh.client` + `exports['./client']`，`dsh-plugin/package.json:8-25`）。因此无需 `dsh plugin add` / 无需改 DSH。
- 实测（只读）：用 harness.log 里的 token GET `http://127.0.0.1:43129/?token=…`，`__DSH_BOOT__` 共 80 条 entries，其中有：

```json

```

  ⇒ **当前 4.0 的 `client.js`（手写 `window.__ModuleLoader__.load` bundle，`client.js:14-19`，只 `require('react')`）确实已在浏览器加载**；同一文件可以继续注册新 slot，无需新增构建/安装步骤。

### 2.2 Slot 注册 API 与作用域（写客户端组件的唯一正确姿势）

- 注册：`ctx.slots.register(options, Component)`（`dsh-client-ui-slots/lib/index.js:164`），`ctx.slots.inject(key, cb)` 等待父级声明后再注册（`dsh-client-ui-slots/README.zh.md`「声明纪律」；`dsh-client-ui-slots/lib/index.js:296-320`）。**只可注册到已被父级声明（declared）的 slot**，声明=渲染授权。
- 四种 kind：`single`（单占位）、`list`（有序条目，支持 `order`）、`keyed`（按键分派）、`chain`（优先级 + select 选择器）。
- 作用域：`root` / `session` / `session-maybe`；**session 作用域 slot 的 `inject` 回调会收到 `sessionId` 作为第一个参数**（`dsh-client-ui-renderer/lib/client.js:432-445` `runInject(entry,binding,actions)` → `args.push(binding.key)`；实例：`dsh-client-ui-schedule/lib/client.js:7510-7519` `inject: (sessionId) => ({...})`）。组件内还可用标准 props：`useSession`（会话快照 selector）、`useSessions`、`useWorkspaces`、`renderSlot`、`renderSlotChain`、`t` 等（`dsh-client-ui-conversation/lib/client.js:17745` 的标准 props 解构；`dsh-client-ui-schedule/lib/client.js:1819` 的 `ScheduleCatalogAction({ useSession, ... })`）。
- 组件业务 props：`inject` 返回对象（可含 `hooks` 标准化 observable、`keyedHooks`、普通字段）；框架用 `standardHookPropName` 把 `hooks.xxx` 变成 `useXxx` 供组件调用（`dsh-client-ui-renderer/lib/client.js:437-470`）。这给了我们“模块级共享 store + 各组件 selector”的标准做法。

### 2.4 结论：当前 `client.js` 还能注册哪些

- **可以**注册到 §2.3 表里任何“未被占用”的 `list/keyed/single` 席位（只要父包已声明；Web 组合默认全部挂载，见 `dsh-web-app/cordis.patch.yml` 的客户端 roster）；
- **可以**新增右栏 tab 类型（`sidebarRightTabs.register`）+ 正文 + 标题/菜单席位；
- **可以**在会话作用域拿到 `sessionId`（`inject(sessionId)`），用标准 `useSession/useSessions/useWorkspaces` 读会话状态；
- **不可以**注册未声明的 slot（会 throw/等待）、不能覆盖 `single` 已占席位、不能从 root slot 拿当前会话、不能改 header 结构/通知中心（需宿主改动）。

## 3. 无感 MVP 设计

### 3.1 设计原则

1. **不打扰**：默认一行/一个 chip；无任务且无 attention 时**零占位、零额外请求**（不渲染即不轮询）。
2. **异常才冒泡**：只有 `priority ≥ 75` 的 attention（approval 90 / approval-timeout 92 / urgent-request 85 / stuck-task 80；`lease-wait 82` 为 API-V4 预留、当前 `buildInbox` 尚未产出）才触发气泡；request 60 / completion 35 只进任务条 popover 的“待协作”列表。
3. **就地闭环**：所有动作在会话页内完成；右侧栏/独立窗口只作为“更多”二级入口。
4. **会话优先**：任务条与气泡的文案直接给出**工具名 + 对象**（例如“回复请求 n-… → session_ask / session_share replyTo=…”），而不是只说“有 2 条待办”。
5. **降级安全**：端点失败/字段缺失 → 隐藏组件，不抛错、不阻断输入；所有组件外包 ErrorBoundary（现有 `PanelErrorBoundary` 可复用）。

### 3.2 组件 A：星桥任务条（Session Task Strip）

**位置**
- A1（MVP 必做）：**`conversation.session.header.utilities`** 的 chip（`order:-10`，排序上先于日程 chip（order -5））。
- A2（MVP 可选，强烈建议）：**`conversation.composer.dock`** 的 1 行/可折叠条（composer 上方，全宽卡片风格；无任务/无待办时不渲染）。这是目前最接近“当前任务条”的常驻位置（Todo dock 同款）。

**展示字段**（来自 `/ambient` 响应，见 §3.7）

```
[🌉] 任务：群「论文推进与写作」· 执行 3/5 · 40%   ｜ 待协作 2 ｜ 待批 1 ｜ 桌面：占用
```

- 无任务但有 attention：只显示 `[🌉] 待处理 2`；
- 无任务无 attention：A1 不渲染、A2 不渲染（完全零占位）；
- 资源冲突（lease owner ≠ 当前会话）时追加 `桌面：被 <handle> 占用`（不暴露全标题）。

**交互**
- 点击 chip → 锚定 popover（参考 ui-schedule 的 `useAnchoredPosition`/`useDismissOnOutsidePointer` 用法，`ui-schedule/client.js:1839` 附近）：
  - 任务线 5 阶段（`taskLines.steps`，check/当前/待办图标）+ 最近 3 条 flow（`taskFlows[task.id]`；合成线暂无 flow 时用 steps 兜底，见 R3）；
  - 「待协作」（`requestTo` 含当前会话的 request，含 id/来自谁/要什么）；
  - 「待审批」（当前会话是议会成员时显示，带 approval id）；
  - 底部动作按钮（见 §3.4）。
- “更多”入口：`打开星桥指挥中心`（保留现有 `openBridgeApp` 能力，作为二级入口；不进入主链路）。

**数据来源**
- `state.taskLines`（leaderId/members 含当前会话；`index.js:1097 buildTaskLines`）、`state.taskFlows`（`index.js:1294 buildTaskFlows`）、`state.inbox.items`、`state.sessions[current].currentTask/openRequestCount/availability`（`index.js:3132-3200`：currentTask 来自未答复 request / 未完成 coordinator 任务 / running）。
- 说明：当前 live state 的 `taskFlows` 为空（仅正式 `kind=task` 才有 flow，合成群任务线没有 → 4.0 R3），因此 MVP 的任务条以 `taskLines.steps` 为主、flow 为辅。

### 3.3 组件 B：注意力气泡（Attention Bubble）

**触发**：`ambient.attention.count > 0`，且存在“与当前会话相关或需用户/会话处理”的项：
- `approval`（待议会审批，priority 90）→ 对议会成员显示“待你投票”，对非成员显示“待议会审批”；
- `approval-timeout`（92）/`urgent-request`（85）/`stuck-task`（80）/`lease-wait`（82，4.1 若 computer-use 暴露 waiters）。

**形态（MVP，零宿主改动）**
- **header 锚定气泡**：attention 新出现时，chip 自动展开一次（带轻微 pulse）+ 计数角标；用户处理后收起。
- **可选 composer 浮 pill**：在 `conversation.composer.dock` 渲染一条紧凑 alert 条（单条时直接带动作按钮）。
- 不做全屏/阻塞式弹窗（避免打扰）；不使用 `shell.overlay` 作为 MVP 主形态（拿不到 sessionId，见 §2.3 缺口）。

**内容**
- 按 priority 取前 3 条：`kind 图标 + 标题（≤30字）+ 来源（handle/小组）+ 一句 detail`；
- 动作按钮（见 §3.4）；底部「全部已读」（`inbox.ack`，新增）+「打开星桥」二级入口。

**只出现一次/消失**
- 用户点击处理或「全部已读」→ `POST /command {action:'inbox.ack', payload:{id}}` → 该条不再冒泡（`unread=false`）；
- 在 `inbox.ack` 落地前，客户端用 `localStorage['session-bridge.ack.<sessionId>']` 记录 `kind:id:ts` 兜底，避免刷新后重复打扰；
- 组件 unmount/切换会话即清除本地高亮。

### 3.4 内联动作矩阵（核心）

| 场景 | 动作 | P0 执行路径（推荐） | 命令/工具 | 说明 |
|---|---|---|---|---|
| 待审批 `approval` | 批准 / 驳回 | **panel 直执行** | `approval.approve`（**新增**）/ `approval.reject`（已有，`index.js:10883`） | panel=用户最高权限；`approvedBy:'panel'` 审计；`approve` 复用 `executeApprovedApproval`（`index.js:2666`） |
| 任意 attention | 标记已读 | **panel 直执行** | `inbox.ack`（**新增**） | 写入 `inbox-ack.json`；attention 重算时过滤已读；`unreadCount` 进 state |
| 待回复请求 `request` | 让本会话回复（要文件/进度） | **steer 当前会话**（P0）/ panel proxy（P1） | `session_ask`（工具） | host 生成指令：`【星桥内联动作】请用 session_ask(group=…, to=…, text=…) 处理 request n-…`；模型执行工具，权限同现有 |
| 催办/提醒 | 催进度 | P0 steer 当前会话 | `session_nudge` | 也可由 panel 直接调（若后续加代理命令） |
| 缺人/招募 | 招募成员 | P1（浮层表单：count/mode/skills）→ steer / panel proxy | `group_recruit` | 需要填写需求，浮层内完成；不切屏 |
| 转交申请 `request`（transfer） | 批准 / 驳回 | P0 steer 当前会话；P1 panel proxy | `task_transfer`（action=approve/reject, requestId=…） | 单条可直接 1-click（参数由 ambient 投影给出） |
| 议会待批 | 投票 approve/reject | **P0 steer 当前会话**（**不 panel 代投**） | `council_vote` | 遵守 4.0「UI 不代投票」（`docs/4.0-architecture.md:424`）；当前会话是议员才显示按钮 |
| 桌面资源冲突 | 查看/等待 | P0 只读展示 + 提示；P1 `resource.status` 刷新 | `resource.status` | `resource.lease.release` 4.2 才有 |
| 查经验 | 搜索 | 不设按钮（可在 popover 给 query 提示） | `session_board action=list` | 会话自然调用 |

**三条执行路径的取舍**

1. **panel 直执行**（approve/reject/ack/claim/retract/wake/urgent/world.post/group.post 等已有或易加）：零延迟、不耗模型 token；但只用于“用户本人授权”的动作，全部审计 `actor.kind='panel'`（HTTP 已注入，`index.js:12686`）。
2. **steer 当前会话**（四工具）：`host` 用 `agent.steer(message)` 注入一条结构化指令，模型在下一步按现有工具执行（保留工具层权限/群成员校验/审计）。优点：不重复实现工具逻辑、不越权；缺点：一次模型回合（秒级 + token），但**由用户点击触发**，可接受。需要新增 host 命令 `ambient.act`（payload: `{sessionId, act:{kind:'ask',...}}`），由 `index.js` 生成安全模板（禁止任意 prompt 拼接；参数白名单）。
3. **深链/右栏**：仅作为“更多”，不满足零切换，不进主链路。

### 3.6 “≤1 次点击 / 零切换”的定义（验收口径）

- **零切换**：动作全程不打开星桥独立窗口、不展开右侧栏、不跳转其它页面/会话。
- **一次点击**：从“会话页可见状态”到“星桥动作已发起”的用户点击次数。
  - 单条场景（唯一待审批/唯一待回复请求/唯一转交申请）：气泡/任务条上直接渲染动作按钮，**1 click 发起**；
  - 多条场景：1 click 打开浮层（动作面），随后在浮层内选择/确认；**不离开会话**；
  - 不可逆动作（approve/reject/转交批准）：建议保留 1 次确认（浮层内），严格口径下记为“1 click 到动作面 + 1 次确认”；若产品要求严格 1-click，可对非破坏动作执行严格 1-click、破坏动作单独豁免并在验收中列明。
- 记录方式：客户端埋点（`ambient.action.click` / `ambient.action.sent`）或验收手工计时。

## 4. 让会话自然优先走星桥（模型侧）

### 4.1 现状：静态规则 + 定向上下文

- **静态硬规则**：`INSTRUCTIONS`（`index.js:217-289`）通过 `ctx.systemPrompt.section({name:'session-bridge:instructions', order: cfg.sectionOrder(650), text: isRootAgent ? INSTRUCTIONS : ''})` 注入（`index.js:4484-4506`）。其中「星桥优先（v4.0）」在 `index.js:227`：

```
**星桥优先（v4.0）**：遇到跨会话问题——找人、要进度、交接、转交、审批、资源冲突、共享经验——
先走星桥：session_board 查经验 → session_ask / session_nudge；缺人用 group_recruit；转交用 task_transfer；
审批用 council_vote。不要直接开子代理硬扛，也不要先问用户。子代理只用于一次性、独立、无需回话的子任务。
```

- **动态定向上下文**：`ctx.systemPrompt.context({name:'session-bridge:board', order:300, required:true, text:(ctx)=>renderForAgent(ctx.agent)})`（`index.js:4506-4513`）；`renderForAgent`（`index.js:3983`）在 `injectMode='targeted'` 时只调用 `renderTargeted`（`index.js:3942`）：仅注入「发给我的未答请求 / 对我请求的回复 / nudge / 未申报提示」（`targetedInteractionEntries`，`index.js:3915-3940`）。
- **缺口**：模型知道“应该用星桥”，但**看不到“我当前的任务/待审批/资源占用/可协作对象”**；于是仍可能先问用户或开子代理。且 `required:true` 的 context 每步重算，成本可控（当前多数会话返回空串）。

### 4.2 新增：ambient 运行上下文块（每步、按需、预算内）

在 `renderForAgent` 返回的 targeted 文本之后追加 `【星桥 · 本会话态势】` 块（≤600 字符；任何字段为空则不输出该行；全部为空则整块不出现 → 零噪声）：

```
【星桥 · 本会话态势】（与当前任务无关可忽略；不要向用户复述）
任务：群「论文推进与写作」· A3 合成闭环 · 阶段 3/5 执行 40%（组长 群管回环/mw0t86pr）
待协作：1 条发给你但未回答的请求：n-mwajlce2「A3 合成闭环：0.104 的误差从哪来」→ 用 session_ask/session_share(replyTo=n-mwajlce2) 处理
待审批：1 条议会待批 ap-…（你是议员）→ 用 council_vote action=vote approve|reject
转交：1 条待你审批的转交申请 req-… → 用 task_transfer action=approve|reject requestId=req-…
资源：桌面被 另一会话(session-xxxx) 占用，TTL 38s；不要抢，先等/先问用户
规则：跨会话问题先走星桥（session_ask / group_recruit / task_transfer / council_vote / session_board）；
      不要开子代理硬扛，也不要先问用户；子代理只用于一次性、独立、无需回话的子任务。
```

实现要点：
- 与 `renderTargeted` 共用 `targetedInteractionEntries` 结果去重（同一 request 不出现两次）；
- 只列 top 1 任务 + top 3 attention + 1 条资源；`maxChars` 截断（沿用 `cfg.maxChars`，默认 460，可对 ambient 单独设 600）；
- **只在“有具体事”时出现**；空态返回 ''（当前 4.0 的目标状态是“没被问到就不注入”，不能退化成广播）；
- 失败 try/catch 返回 ''（不能因 ambient 抛错导致 `assemble()` 失败、整轮发不出请求——现有 `INSTRUCTIONS` 注释也强调过类似风险）。

### 4.3 评估：哪些提示/状态能让会话自然优先走星桥

| 手段 | 有效性 | 说明 |
|---|---|---|
| 静态「星桥优先」长规则（已有 2000+ 字 INSTRUCTIONS，`index.js:217-289`） | 中 | 必要保底，但长文在长上下文里权重低；模型常“知道但不做” |
| **ambient 动态块：具体待办对象 + 工具名 + 参数模板** | 高 | 模型最缺“此刻有什么、找谁、填什么参数”；给出 `request id / contactId / approvalId` 后触发率显著高于泛泛规则 |
| 负向约束（“不要开子代理/不要先问用户”）放在 ambient 块尾句 | 高 | 与具体对象同屏出现，比只放在静态规则里强 |
| `required:true` 每步刷新（`ctx.systemPrompt.context`） | 高 | 任务/审批状态变化后下一步即可见；已有机制 |
| UI 与上下文同源（用户看到的 chip/气泡 = 模型看到的 ambient 行） | 中高 | 用户可纠正/点击，形成“人机同视图” |
| 只给数字（“待处理 2 条”） | 低 | 模型无法行动，容易转而问用户 |
| 只靠工具描述（session_ask 等已很长） | 中低 | 工具存在但模型不知道有对象可用 |
| 空态也注入“星桥无事” | 负面 | 浪费 token、稀释注意力；必须零注入 |

结论：**ambient 动态块是把「星桥优先」从“规则”变成“行为”的关键**；成本低（仅在有发生时 ≤600 字符），风险可控（纯 host 插件、可回滚）。

### 4.4 端到端场景（模型侧证据链）

| 用户/会话场景 | ambient 行（模型看到） | 期望模型行为 |
|---|---|---|
| 用户问「第 3 章初稿/进度」且群里有待回复 request | `待协作：1 条…n-xxx → session_ask/session_share(replyTo=n-xxx)` | 首选 `session_ask` 向群成员要进度，而不是开 subagent/问用户 |
| 群任务缺人、我是群管理 | `缺人：群「…」任务「…」→ group_recruit(...)` | 首选 `group_recruit`，而非硬派老人/开子代理 |
| 收到转交申请 | `转交：… → task_transfer action=approve requestId=…` | 直接 `task_transfer`，不新建任务 |
| 议会待批且我是议员 | `待审批：ap-… → council_vote` | 直接 `council_vote`，不催用户 |
| 桌面被占用且我要用 computer-use | `资源：桌面被 X 占用 TTL…；不要抢` | 先等/告知用户，不盲目重试 |

### 4.5 权限与防退化

- **panel 动作**走 HTTP command（`actor.kind='panel'`，`index.js:12686`），审计字段 `approvedBy:'panel'`/日志；仅限“用户本人可拍板”的动作。
- **council_vote 不由 panel 代投**（遵守 `docs/4.0-architecture.md:424`）；按钮只出现在“当前会话是议员”的会话里，执行方式是 steer 该会话 → 模型调 `council_vote`。
- **steer 指令由 host 生成**：`ambient.act` 只接受白名单 `kind + 参数`，host 模板渲染为固定中文指令（禁止客户端传任意 prompt），并在 `index.js` 内限频（同一会话同一目标 10s 一次）、记录来源 `source.kind='session-bridge-ambient'`。
- **不伪造用户消息**：steer 消息 source 用插件专属 kind（参考 time-context 的 snapshot source 形式：`{kind:'session-bridge', form:'snapshot', sections:[…]}`），UI 可区分。
- **隐私**：ambient 只返回当前会话相关项；其他会话用 handle/短 id；不返回规则全文、不返回他人 cwd。

## 7. 风险与待决问题

1. **全量 state 太重**：392KB/5s 不可接受 → 必须新增 `/ambient`；若暂不做端点，MVP 不可上线（先做端点）。
2. **“顶部”语义**：DSH 无全宽顶部 banner 席位；MVP 用 header chip（顶部）+ composer dock 条（全宽）覆盖。若产品坚持字面全宽顶部 → P2-1（改 DSH），需另立任务。
3. **不可逆动作的 1-click 风险**：approve/reject 建议保留确认；与“≤1 次点击”口径需产品确认（§3.6）。
4. **council_vote 权限**：坚持“UI 不代投票”，用 steer 当前议员会话方式；若产品要求面板直接投，需要治理层明确授权（不建议）。
5. **模型忽略 ambient**：需要在 prompt 里给对象+工具模板；用 5 场景回归量化；必要时对 `inbox` 中的 urgent/approval 再加一条 `session_nudge` 级提醒（仍不唤醒）。
6. **双份数据/不一致**：客户端 UI 与模型上下文必须来自同一 `buildAmbient`，避免“看到的不等于模型看到的”。
7. **client.js 热更新**：client bundle rev 由文件 mtime/size 派生，页内是否即时替换取决于 client-hmr；最稳妥为刷新页面（不影响 host 热更）。4.1 验收脚本需覆盖“刷新后一致”。
8. **poll 负载**：29 活会话若各自轮询，host 需 memo/缓存（`buildAmbient` 5s memo）；客户端同一页面只允许一个 ambient 轮询（多组件共享 store）。
9. **隐私**：ambient 只输出当前会话相关项；其他会话只用 handle/短 id；不得把规则全文塞进 UI 或上下文。
10. **待决**：`inbox.ack` 的存储（新文件 `inbox-ack.json` vs deliveries 复用）；`unreadCount` 契约是否进 4.1（API-V4 已预留）；`/events?sinceSeq` 是否替代轮询（4.0 可选未实现）。
