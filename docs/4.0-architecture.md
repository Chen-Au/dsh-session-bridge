## 0. 一页结论

1. **分层**：`board.jsonl（事件源） → 纯函数投影（taskLines/taskFlows/inbox/computerResource） → HTTP API（state/command） → 星桥窗口 UI`。UI 不读盘、投影不写盘、命令是唯一写入口。
2. **四个领域**：`taskFlow`（任务生命周期 + 信息流）、`inbox`（人/议会要处理什么，派生读模型）、`governance`（小议会审批 + 官职/权限/暂停）、`resourceLease`（computer-use 等独占资源的优先级/租约/队列）。
3. **统一事件模型**：新增 `events.v4.jsonl`，`board.jsonl` 保留为兼容视图；事件 envelope 带 `eventId/type/actor/subject/dedupeKey/seq`，写入前幂等去重；投影只从事件派生，杜绝“同一事实两种写法”。
4. **兼容**：全部改动是 **additive**——旧 state 字段一个不删、旧事件 `op` 不删、新文件新代码才读；旧版本读到新数据只会忽略。回滚 = 换回旧插件包，数据不迁移、不破坏。
5. **首屏**：星桥 = 跨会话控制面，首屏只回答三个问题：**有什么需要我拍板/异常？任务流到哪一步？桌面资源现在归谁？** 统计、积分榜、社交能力全部降级到二级页。

## 1. 目标、非目标与成功指标

### 1.1 目标

| # | 目标 | 可验收结果 |
|---|---|---|
| G1 | 用户打开星桥后 **5 秒内**知道“现在该做什么” | 首屏 P0 区展示：待审批 N、卡住 N、加急/求助 N；每条可一键处理或跳转 |
| G2 | 任务从创建到收口有**唯一信息流** | 任一任务卡可展开时间线：创建→指派→派发→回复→交接→完成/撤回，事件不重复、顺序稳定 |
| G3 | 跨会话异常**自动冒泡**，不靠用户巡场 | 卡住（>25min）、待审批、排队超时、资源租约异常进入统一收件箱 |
| G4 | computer-use 等独占资源**可解释地排队** | state 能看到当前持有者/剩余 TTL/优先级；高优先级可解释地先拿 |
| G5 | 升级/回滚**零数据迁移风险** | 旧包+新数据可启动；新包+旧数据可启动；`node test/contract.mjs` ALL PASS |

### 1.3 非目标（4.0 不做）

- 不做可视化拖拽式 DAG 任务编排（保留 5 阶段清单）。
- 不做多机分布式一致性（星桥仍是**单机本地文件**协作层；跨机靠远程访问方案）。
- 不做通用 issue tracker / 项目管理 SaaS；bug 群仍是“请求池”。
- 不改 DSH 宿主接口；不引入第三方运行时依赖（保持“纯 ESM、零依赖”约束，见 `index.js:26-30`）。

### 1.2 成功指标（上线后 7 天可量测）

| 指标 | 现状（v3.x 估算） | 4.0 目标 |
|---|---|---|
| 首屏到“处理动作”点击数 | 3~5 次（首页→群聊→找卡片） | ≤1 次 |
| 卡住任务平均被发现时间 | 靠催办/巡场，>1h | <5min（进入收件箱即提示） |

## 3. 分层架构

### 3.1 四层模型

```
┌──────────────────────────────────────────────────────────────────────┐
│ L3 UI 层：星桥窗口 (app.html) / 右侧栏 (client.js) / 未来面板          │
│   只做：拉 state、渲染、发 command、深链跳转（不读盘、不推导业务规则）      │
├──────────────────────────────────────────────────────────────────────┤
│ L2 API 层：HTTP（state / command / priority / events / app / file）    │
│   只做：鉴权(loopback+CSRF)、入参校验、调命令、返回 {result, state}       │
├──────────────────────────────────────────────────────────────────────┤
│ L1 领域投影层（纯函数，无副作用，可单测）                                │
│   taskFlow  │  inbox(read model)  │  governance  │  resourceLease      │
│   输入：events + groups；输出：state.*；不写盘                          │
├──────────────────────────────────────────────────────────────────────┤
│ L0 事件源层（append-only 本地文件）                                     │
│   board.jsonl(兼容视图)  events.v4.jsonl(4.0 真相)  groups.json         │
│   approvals.json  council.json  offices.json  pauses.json  …           │
│   规则：只有 executeCommand / 事件写入器能写；写入 = 幂等 + 顺序号         │
└──────────────────────────────────────────────────────────────────────┘
```

### 3.2 硬性规则（违反即架构回退）

1. **UI 不读盘**：app.html 只能 `fetch('/api/session-bridge/state')` 与发 command；禁止再出现“前端自己从 entries 拼任务线/inbox”的新逻辑（现有 v3 逻辑保留但冻结）。
2. **投影是纯函数**：`buildTaskLines/buildTaskFlows/buildInbox/buildComputerResource` 只接收数据快照 + `now`，不读环境、不写盘、不发网络（`computerResource` 例外：它是 L2 资源适配器，见 §8）。
3. **单一写入口**：所有业务写操作 = `executeCommand(action, payload, actor)`；事件写入器只被它和极少数生命周期钩子调用。
4. **事件 append-only**：`events.v4.jsonl` 永不修改行；更正靠新事件（`*.retracted`、`*.superseded`）。
5. **state 只增不删**：新版本可加字段，绝不删/改旧字段语义；旧 UI 看到新 state 忽略未知字段。
6. **可回滚**：任何新文件/新事件类型，旧代码必须能安全忽略（`foldEvents` 的 if/else-if 天然满足）。

### 3.3 数据流（一次“完成任务”的完整路径）

```
agent 调 session_share(replyTo=requestId, kind=handoff)
  → tool execute
    → executeCommand('share.post' 或工具内 addEntry/patchEntry)
      → ① appendBoardEvent(op=answer) / patchEntry(taskStatus=done)      [L0 兼容视图]
      → ② appendEventV4('request.answered' / 'task.completed', actor,…)  [L0 4.0 真相]
      → ③ completionNotice 生成（幂等，基于事件去重）
  → stateForUi()
      → buildTaskLines(events, now)      → state.taskLines
      → buildTaskFlows(events)           → state.taskFlows
      → buildInbox(...)                  → state.inbox / commandCenter
  → UI 5s 轮询拿到新状态 → 首页 P0 消失 / 任务线 done / 完成通知
```

## 4. 四个领域服务边界

> 约定：**Owns** = 只此域可写；**Reads** = 只读依赖；**Emits** = 产生的事件类型；**Commands** = 对外动作；**State** = 暴露字段；**Invariants** = 必须保持的不变量。

### 4.1 `taskFlow`（任务生命周期 + 信息流）

| 项 | 内容 |
|---|---|
| 职责 | 任务/请求/交接/完成通知的生命周期与**唯一信息流**；阶段清单推进；卡住判定；催办节流 |
| Owns | `board.jsonl` 中 `kind∈{task,request,handoff,note}` 的生命周期字段（`taskStatus/coordinator/assignees/owner/steps/taskScope/completionNotice`）；`taskFlows` 派生 |
| Reads | groups（成员/群管理）、sessions（身份/availability）、events（4.0 后） |
| Emits | `task.created` `task.assigned` `task.delegated` `task.replied` `task.handoff` `task.completed` `task.reassigned` `task.retracted` `task.paused` `task.resumed`（后 4 个为补全状态机） |
| Commands | `world.post` `group.post` `session_ask`(task 模式) `task.claim` `task.release` `task.dedupe` `task.pause` `task.resume` `task.transfer`（已有） |
| State | `taskLines` `taskLineStats` `taskFlows` `completionNotices` `completionStats` `commandCenter.activeTasks` |
| Invariants | ① 一个任务同一时刻最多一个 active owner；② `taskStatus=done` 必须有 owner 或 coordinator 的完成事件；③ 信息流事件时间单调（同 ts 按 seq）；④ 每任务 flow ≤40 条；⑤ 完成通知每任务仅一次（幂等键 `taskId:completed`） |
| 不负责 | 谁能操作（governance）、未读状态（inbox）、资源排队（resourceLease） |
| 文件 | `board.jsonl`（现行）、`events.v4.jsonl`（4.0） |

### 4.2 `inbox`（统一收件箱，**派生读模型**）

| 项 | 内容 |
|---|---|
| 职责 | 把“需要人/议会处理的事”聚合成一个稳定列表；计算 attention/未读；提供跳转目标 |
| Owns | `inbox-state.json`（4.0 新增：已读游标、静音项）——**只存读状态，不存业务事实** |
| Reads | approvals（governance）、open requests（taskFlow）、taskLines、pendingAsks、completionNotices、computerResource 异常 |
| Emits | 无业务事件；仅 `inbox.acked`（审计可选） |
| Commands | `inbox.ack`（id/all）`inbox.mute`（kind/窗口）`inbox.act`（见 §6.4） |
| State | `inbox:{items,attention,total,attentionCount,unreadCount,generatedAt}`、`commandCenter.attentionCount/inboxCount` |
| Invariants | ① 纯派生：删除业务对象后 item 自动消失，不留孤儿；② 同 `(kind,id)` 只出现一次；③ 排序稳定（priority desc, ts desc, id asc）；④ 已读不回写业务对象 |
| 不负责 | 决定谁有权限（governance）、任务状态（taskFlow） |
| 文件 | `inbox-state.json`（新增，可缺失） |

### 4.3 `governance`（小议会 / 官职 / 权限 / 暂停）

| 项 | 内容 |
|---|---|
| 职责 | 审批与小议会决策；官职与军功；权限授予；维护者保护；暂停/恢复；审计 |
| Owns | `council.json` `approvals.json` `offices.json` `permissions.json`（`readPermissionsOf`）`maintainer.json` `pauses.json` |
| Reads | sessions、groups、reputation、events |
| Emits | `council.formed` `approval.requested` `approval.voted` `approval.resolved` `approval.executed` `approval.escalated` `office.promoted` `permission.granted` `permission.revoked` `pause.set` `pause.cleared` |
| Commands | `council_vote`(工具) `approval.list` `approval.reject` `approval.escalate`(新) `office.*` `perm.grant/revoke` `maintainer.set/get` `task.pause/session.pause/task.resume/session.resume` |
| State | `council` `approvals`（pending）`offices` `officeCatalog` `officePromotionRules` `permissions` `maintainer` `pauses` `capabilities.protectionLevels/interrupt/retract` |
| Invariants | ① 审批终态唯一（approved/rejected/canceled）；② 同一 approval 只执行一次（幂等键 `approvalId:executed`）；③ 维护者永不进入自动路由；④ quorum=ceil(成员/2)，票数达到即终态；⑤ 所有决策留审计事件 |
| 不负责 | 任务执行细节、UI 展示、资源租约 |
| 文件 | 见上 |

### 4.4 `resourceLease`（独占资源优先级与租约，4.0 新建）

| 项 | 内容 |
|---|---|
| 职责 | 为 `computer-use`（桌面）、未来的 browser/terminal/engine 等**独占资源**提供统一优先级、租约可见性、排队与抢占规则 |
| Owns | `state.computerResource`（扩展）、`resources.json`（可选：资源注册表）、`lease-events`（审计） |
| Reads | computer-use 租约文件 `%LOCALAPPDATA%\dsh-computer-use\lease\desktop-lease.json`、computer-use 的 `waiters.json`（4.1 新增，可选）、governance 官职/军功、任务紧急度 |
| Emits | `lease.acquire.requested` `lease.granted` `lease.renewed` `lease.released` `lease.expired` `lease.preempted` `lease.queued` |
| Commands | `resource.status` `resource.lease.release`（管理员强制释放）`resource.priority`（调试）——**不新增 acquire**：acquire 仍由 computer-use 插件执行，星桥只提供优先级与可见性 |
| State | `computerResource:{schemaVersion,available,resourceId:'desktop',lease:{owner,label,expiresAt,ttlMs,heldByMe?},priority,office,queue?:[{sessionId,priority,seq,waitingMs}],degraded?}` |
| Invariants | ① 一个资源同一时刻最多一个租约持有者；② 优先级仅在**等待**时决定次序，不抢占已持有者（除显式 `preemptible`）；③ TTL 到期即视为释放；④ 星桥不伪造租约状态（读不到就 `available:false`） |
| 不负责 | 实际键鼠注入/引擎生命周期（computer-use 插件 + Python 引擎） |
| 文件 | 只读 computer-use 租约文件；可选写 `resources.json` |

### 4.5 域间协作

```
governance ──approval.requested──▶ inbox(P0)
governance ──approval.resolved(grant)──▶ resourceLease?  (间接：审批通过才创建会话，会话再抢资源)
taskFlow  ──task.completed──▶ inbox(P2 completion) + taskFlows
taskFlow  ──lineStatus=stalled──▶ inbox(P0) + 催办插话
resourceLease ──lease.expired/queue 异常──▶ inbox(P1)
inbox ──ack/act──▶ 只写 inbox-state.json + 发既有 command（不改业务事实）
```

**禁止**：inbox 直接改任务状态；resourceLease 直接改审批；taskFlow 直接调 computer-use 工具。跨域只通过事件 + command。

## 5. 统一事件模型 v4

### 5.1 Envelope

```json
{
  "v": 4,
  "seq": 12345,
  "id": "ev-<seq>-<hash8>",
  "type": "task.assigned",
  "ts": 1794303194786,
  "actor": { "kind": "session|panel|tool|system", "id": "session-...", "name": "handle/用户" },
  "subject": { "kind": "task|request|approval|lease|group|session|office|resource", "id": "n-..." },
  "payload": { },
  "dedupeKey": "task:assigned:<taskId>:<ownerId>",
  "source": { "surface": "tool|panel|timer|system", "command": "session_ask|group.post|…" },
  "causedBy": "ev-<seq>-<hash8>|null"
}
```

- `seq`：单文件单调递增（启动时读最后一条 seq，写入前 +1；单进程写，天然有序）。
- `id`：`ev-${seq}-${sha1(type|subject.id|dedupeKey|ts).slice(0,8)}`。
- `actor`：`panel`＝用户/面板；`session`＝某个会话；`tool`＝模型工具调用；`system`＝定时器/巡检。
- `subject`：事件作用对象；`causedBy` 用于串联（vote→resolved→executed）。

### 5.2 事件目录（4.0 必选集合）

| 域 | type | subject | 关键 payload | 幂等键 |
|---|---|---|---|---|
| taskFlow | `task.created` | task | `{title, groupId, coordinator, assignees, steps, taskScope, worldTask}` | `task:created:<taskId>` |
| | `task.assigned` | task | `{coordinator, assignees, owner, ownerRole}` | `task:assigned:<taskId>:<owner>` |
| | `task.delegated` | request | `{taskId, from, to[], step, requestId}` | `task:delegated:<requestId>` |
| | `task.replied` | request | `{taskId, requestId, replyId, by, proposal?, verdict?}` | `task:replied:<requestId>` |
| | `task.handoff` | task | `{taskId, from, to, files[], summary}` | `task:handoff:<entryId>` |
| | `task.completed` | task | `{taskId, by, closingStatus, needUser}` | `task:completed:<taskId>` |
| | `task.reassigned` | task | `{taskId, from, to, reason, approvalId?}` | `task:reassigned:<taskId>:<to>` |
| | `task.retracted` | entry | `{entryId, by, reason}` | `entry:retracted:<entryId>` |
| | `task.paused` / `task.resumed` | task/session | `{targetId, reason}` | `pause:<id>:<at>` |
| governance | `council.formed` | group | `{groupId, members[], chair}` | `council:formed:<groupId>` |
| | `approval.requested` | approval | `{source, groupId, requester, route, memberCount, text}` | `approval:requested:<approvalId>` |
| | `approval.voted` | approval | `{voter, vote, reason, approveCount, rejectCount, quorum}` | `approval:voted:<approvalId>:<voter>` |
| | `approval.resolved` | approval | `{outcome, approveCount, rejectCount, quorum}` | `approval:resolved:<approvalId>` |
| | `approval.executed` | approval | `{result:'ok'|'error', detail}` | `approval:executed:<approvalId>` |
| | `office.promoted` | session | `{from, to, merit}` | `office:promoted:<sessionId>:<to>` |
| | `permission.granted/revoked` | session | `{targetId, by}` | `perm:<action>:<targetId>:<at>` |
| resource | `lease.acquire.requested` | resource | `{resourceId, sessionId, priority}` | `lease:req:<resourceId>:<sessionId>:<tsSec>` |
| | `lease.granted` | resource | `{resourceId, owner, expiresAt}` | `lease:granted:<resourceId>:<owner>:<acquiredAt>` |
| | `lease.renewed` | resource | `{resourceId, owner, expiresAt}` | `lease:renewed:<resourceId>:<expiresAt>` |
| | `lease.released` | resource | `{resourceId, owner, how:'explicit'|'ttl'|'forced'}` | `lease:released:<resourceId>:<owner>:<expiresAt>` |
| | `lease.queued` | resource | `{resourceId, sessionId, priority, seq}` | `lease:queued:<resourceId>:<sessionId>:<seq>` |
| entry | `entry.created` / `entry.retracted` / `entry.answered` | entry | 最小字段 | `entry:<op>:<entryId>` |

> 规则：**一个业务事实只发一条事件**。例如任务的“派发”只发 `task.delegated`，不再同时发 `entry.created(kind=request)` 之外的重复事件；`entry.created` 仅用于 note/handoff/chat 这类纯内容条目。

### 5.3 状态机

```
task:    created → assigned → delegating → collecting → done
                       ↘ canceled/retracted
                       ↘ paused ⇄ resumed
request: open → queued(依赖) → open → answered
                              ↘ canceled/failed
approval: pending → approved → executed
                  ↘ rejected
                  ↘ canceled(撤回) / escalated(超时)
lease:   (none) → acquired → renewed* → released/expired
                  ↘ queued → acquired
```

非法迁移一律拒绝并写 `*.rejected` 审计（不改变业务状态）。

### 5.4 去重与幂等（关键）

1. **写入前查重**（同一个 `dedupeKey` 在 24h 内已存在 → 丢弃并返回 `{ok:true, deduped:true}`）。
   - 内存 Map（启动时从事件文件回填最近 5000 条）+ 写入文件后更新；跨重启靠回填。
2. **命令幂等**：`POST command` 支持可选 `requestId`（客户端生成 uuid）；`receipts.jsonl` 记录 `requestId → 结果摘要`，重复请求直接回放结果（防双击/重试造成双发任务）。
3. **投影去重**：`taskFlows` 按 `(type,subject.id,ts)` 排序后去重；同一事件被 board 兼容层重放不会产生重复 flow（flow 由 v4 事件生成后，board 不再参与 flow）。
4. **完成通知幂等**：`taskId:completed`；重复 done 或撤回后重发都不生成第二条。
5. **幂等边界**：`entry.created` 以 entry id 为键；`approval.voted` 以 `(approvalId,voter)` 为键（改票覆盖旧票，事件仍只留最后一条有效 + 审计）。

### 5.5 落盘与回放

| 项 | 规格 |
|---|---|
| 文件 | `<boardDir>/events.v4.jsonl`（append-only，每行一个 envelope） |
| 写入 | `appendEventsV4(events[])`：计算 seq → 去重 → `appendFileSync` 一行一批；失败重试 1 次后回退（事件不写不阻塞业务，记 warn） |
| 回放 | 启动时读最后 2000 条回填 dedupe Map 与 `lastSeq`；完整回放在需要时（contract 测试/导出） |
| 压缩 | 每 30 天或 8MB 触发：保留最近 90 天 + 所有 `*.completed/approved/lease.*` 终态事件；压缩前备份 `events.v4.jsonl.bak` |
| 游标 | `GET /api/session-bridge/events?sinceSeq=N&limit=500` 只读导出（调试/审计；UI 不用） |
| 与 board 关系 | **4.0：双写**（board 仍为 tab/UI 兼容真相，events 为新真相）；4.1 起投影以 events 为准，board 降级为兼容视图，可再评估是否停写 |

### 5.6 旧 board 事件 → v4 事件映射（迁移实现清单）

| 旧 `op` | 触发点 | v4 事件 |
|---|---|---|
| `add`（kind=task） | `addEntry` | `task.created`（+ `entry.created` 若需要内容流） |
| `add`（kind=request） | `addEntry` | `task.delegated`（有 taskId）或 `entry.created` |
| `add`（kind=handoff/note/chat/bug） | `addEntry` | `entry.created` |
| `task`（patch） | `patchEntry/patchTaskEntry` | 按 patch 字段：`coordinator/assignees`→`task.assigned`；`taskStatus=done`→`task.completed`；`taskStatus=canceled`→`task.retracted`；`paused`→`task.paused` |
| `answer` | `appendEvents(answer)` | `task.replied`（+ `task.completed` 若闭环） |
| `claim`/`unclaim` | `appendEvents` | `task.assigned`（claimState 变化）或 `entry.claimed` |
| `retarget` | `appendEvents` | `entry.retargeted` |
| `remove` | 撤回 | `task.retracted` / `entry.retracted` |
| `deliver`/`accept` | 送达/接受 | `entry.delivered` / `entry.accepted`（保留在 deliveries.jsonl，事件仅审计） |

## 6. 统一收件箱（inbox）设计

### 6.1 定位

**inbox 是读模型**：不拥有任何业务状态，只把“已存在的事实”翻译成“需要谁处理”。因此：

- 新增业务能力 → 只需加一条“生成规则”，不需要迁移数据；
- 业务对象撤回/完成 → item 自动消失（无孤儿清理）；
- 已读状态单独存 `inbox-state.json`，与业务解耦。

### 6.2 Item schema

```json
{
  "id": "approval:ap-xxx",
  "kind": "approval|request|urgent-request|stuck-task|paused-task|queued-ask|completion|lease-wait|approval-timeout",
  "priority": 90,
  "ts": 1794303194786,
  "title": "待议会审批：招募 3D 建模成员",
  "detail": "新成员招募 · 群「shoot_game · 招募协作」",
  "groupId": "g-...",
  "groupName": "…",
  "taskId": "n-...",
  "sessionId": "session-...",
  "action": "open-approval|open-group|open-task|open-session|open-resource|open-world",
  "target": { "view": "tasks", "groupId": "g-...", "taskId": "n-...", "approvalId": "ap-..." },
  "actions": [{ "id": "approve", "label": "批准", "command": { "action": "council.vote.panel", "payload": { "approvalId": "ap-..." } } }],
  "unread": true,
  "createdAt": 1794303194786,
  "expiresAt": 0
}
```

### 6.3 生成的 kind / 优先级（保持并扩展当前实现）

| kind | 来源 | priority | 默认动作 |
|---|---|---|---|
| `approval` | approvals pending | **90** | `open-approval` |
| `approval-timeout`（新） | pending 超 30min | **92** | `open-approval` + 可 `escalate` |
| `urgent-request` | request.urgent | **85** | `open-group` |
| `lease-wait`（新） | computerResource.queue 中有己方等待 > N 秒 | **82** | `open-resource` |
| `stuck-task` | taskLines stalled | **80** | `open-task` |
| `request` | open request（非 urgent） | **60** | `open-group` |
| `paused-task` | paused | **50** | `open-task` |
| `queued-ask` | pendingAsks queued | **45** | `open-group` |
| `completion` | completionNotices | **35** | `open-task` |
| `lease-holder`（新，非待办） | 当前租约持有者（信息项） | 20 | `open-resource` |

`attention` = `priority >= 75`（保持当前阈值 75）。`unreadCount` = 未 ack 的 attention 项数。

### 6.4 已读、动作与跳转

- `inbox-state.json`：`{version:1, sessions:{<sessionId>:{acked:{<itemId>:ts}, mutedKinds:{...}, lastSeenAt}}}`（按会话区分：用户面板一个 session key，`panel`）。
- `inbox.ack`：标记单条/全部已读；只写 `inbox-state.json`，不触发事件。
- `inbox.mute`：按 kind 静音 N 分钟（如 completion）。
- **动作执行**：UI 不直接拼业务命令——item.actions 里带 `command`，前端 `POST /command` 照发；服务端校验权限（governance 规则）。
- **跳转协议**（UI 内部 hash 路由，不新增 HTTP）：
  `#/tasks?taskId=…`、`#/groups?groupId=…`、`#/approvals?approvalId=…`、`#/resource/desktop`、`#/world`。
  `target` 字段是唯一权威，禁止 UI 用 title 猜。

### 6.5 与完成通知/panelMention 的关系

`completionNotices` 继续作为“完成事件”的数据源；inbox 的 `completion` 是其**展示投影**。`panelMention`/`needUser=是` 的完成通知优先度提到 75（进入 attention），普通完成保持 35（只占未读）。

## 7. 小议会审批如何接入同一事件模型

### 7.1 现状（v3.4，已实现，不重写）

- 议会：`council.json`（`members≤3`，`chair` 最高官职），自动群 `星桥 · 小议会`（`kind:'council'`）。
- 审批：`approvals.json`（`id/status/source/engine/groupId/title/text/reason/requester/payload/votes/…`）。
- 投票：`council_vote` → `approval.votes[voter]={vote,reason,at}`；`quorum=ceil(members/2)`；`approveCount>=quorum→approved`、`rejectCount>=quorum→rejected`；approved 立即执行（`executeApprovedApproval`）。
- 通知：`notifyCouncilApproval` 建议会群请求 + 唤醒成员。

### 7.2 事件化（4.0 增量）

| 时机 | 事件 | 说明 |
|---|---|---|
| 创建 approval | `approval.requested` | 同时进 inbox（priority 90） |
| 每次投票 | `approval.voted` | 幂等键含 voter；改票覆盖 |
| 达到法定票数 | `approval.resolved` | outcome 固化，之后投票拒绝 |
| 执行成功/失败 | `approval.executed` | `causedBy=resolved` 事件 id；失败→inbox P0 + 通知 chair |
| 超时（30min 无票） | `approval.escalated` | 转用户面板（inbox P0 标题带“交还用户”），不再等议会 |

### 7.3 UI 接入

- 首屏 P0「待议会审批」卡片：标题/类型/法定进度（`approveCount/quorum`）、`[批准] [驳回] [交还用户]`。
- 面板（user/panel actor）可直接 `approval.approve/reject`（现有 `approval.reject`；新增 `approval.approve` 供面板直批，绕过 quorum，写 `approval.resolved` by=panel）。
- 议会成员在自己会话里仍用 `council_vote` 工具；UI 不代投票（避免越权）。

### 7.4 权限与优先级

- 谁可看/处理：`panel` > `maintainer` > `council` 成员 > 群管理。rate-limit：同一 approval 同一人 1 票。
- 优先级：`approval` 90 > `urgent-request` 85 > `stuck` 80。议会审批不可被 `inbox.mute` 静音（P0 恒定）。

### 7.5 幂等执行与回滚

- `executeApprovedApproval` 前查 `approval.executedAt`；已执行直接返回 `{deduped:true}`。
- 执行失败不回滚审批（审批结论有效），写 `approval.executed{result:'error'}` + inbox P0 + 日志；由 maintainer/用户重试或改派。

## 8. computer-use 资源优先级/租约接入

### 8.1 现状（真实的两个进程）

```
computer-use 插件 (DSH profile plugin)
  ├─ 工具 execute 前置：computerPriorityOf(owner) → GET 星桥 /computer/priority?owner=
  ├─ computerWaiters 队列（内存，priority desc → seq asc）
  ├─ acquireComputerTurn(owner, priority)
  └─ Python 引擎：桌面租约文件 %LOCALAPPDATA%\dsh-computer-use\lease\desktop-lease.json
        {version,owner,label,pid,engine_version,acquired_at_ms,expires_at_ms,last_cmd}
        TTL 默认 45s，mutating 自动续期；acquire/release/lease 动作；DESKTOP_BUSY/NOT_LEASE_OWNER/LEASE_UNSUPPORTED/PANIC_ACTIVE
```

星桥侧现状：只读租约文件给 `state.computerResource`；提供 `priority = officeLevel*10000 + points`。

### 8.2 resourceLease 域（4.0 最小模型）

```json
// state.computerResource（扩展后）
{
  "schemaVersion": "4.0.0",
  "ok": true,
  "available": true,
  "resourceId": "desktop",
  "label": "Windows 桌面（computer-use）",
  "lease": {
    "owner": "session-eb858fd2-...",
    "ownerName": "论文写作-第一篇",
    "label": "session:33eb6158",
    "acquiredAt": 1794303096663,
    "expiresAt": 1794303194786,
    "ttlMs": 98123,
    "heldByMe": false
  },
  "priority": { "scale": "office*10000+points", "current": 800000, "office": "首席技术员", "points": 12 },
  "queue": [],
  "degraded": false,
  "observedAt": 1794303195000
}
```

- `queue` 在 4.0 为 `[]`（computer-use 尚未暴露 waiters）；4.1 computer-use 写 `%LOCALAPPDATA%\dsh-computer-use\state\waiters.json`（`[{sessionId,priority,seq,waitingMs}]`）后星桥只读展示。
- `degraded:true` 用于：租约文件不存在/损坏、computer-use 未安装、优先级端点不可达。

### 8.3 优先级规则（统一公式）

```
priority(session) =
    officeLevel(0..100) * 10000
  + reputationPoints(max 0)
  + interactivityBoost(用户正在等待 +3000 / 加急 +2000 / 任务截止近 +1000 / 后台巡检 0)
  + aging(已等待分钟数 * 50, 上限 3000)
```

- 数值必须**稳定可复现**（同一秒内相同输入相同输出），便于 UI 解释“为什么他先”。
- 维护者/运维总管（level 90）天然最高；用户面板显式操作可直接要求 `preempt`（需 computer-use 支持；4.0 仅提示“请先释放/等待 TTL 到期”）。
- 独占不抢占：除非资源声明 `preemptible:true` 且新优先级高出 10000 以上（暂不启用）。

### 8.4 与 computer-use 的接口契约（跨仓库，分阶段）

| 阶段 | 星桥 | computer-use |
|---|---|---|
| 4.0（本次） | 修好 `/computer/priority` 注册（R1）；`state.computerResource` 增加 `schemaVersion/ownerName/priority{…}/degraded/observedAt`；写发现文件 `<boardDir>/bridge.json`（`{apiBase,port,updatedAt}`） | 读取 `bridge.json` 优先于硬编码 43129；其余不变 |
| 4.1 | 读 `waiters.json` 展示队列位置、等待时长；资源页 | 每次队列变化写 `waiters.json`；release/expire 时清理 |
| 4.2 | 支持 `resource.lease.release`（管理员强制释放，写 `lease.released{how:'forced'}` 审计） | 引擎支持 `lease_release_force`（owner 校验由星桥授权） |

### 8.5 风险

- **硬编码端口**（R8）：先加发现文件，computer-use 侧改一行即可；不改则换端口后优先级静默归零（degraded）。
- **跨进程队列不可见**：4.0 不假装能展示队列，`queue:[]` + `degraded` 说明；UI 文案不得承诺“排队第 N 位”。
- **抢占安全**：键鼠注入中途抢占会造成半截操作；只允许在 `lease.released` 后按优先级取，禁止硬抢。
- **PANIC/急停优先**：panic 永远最高，不受租约影响（computer-use 既有语义，星桥只展示）。

## 10. UI 信息架构：为什么用户会先看星桥

### 10.1 用户为什么需要星桥（而不是只看 DSH 原生会话）

DSH 原生界面是**单会话视角**：用户只能看到自己正在聊的这一个 agent。一旦把活分出去（世界任务/群任务/多个会话并行），三件关键信息就消失了：

1. **谁在等我拍板**——议会审批、待复核、加急请求，散落在不同会话/群里；
2. **活卡在哪**——任务线 25 分钟没进度、某会话 busy 却没人催；
3. **独占资源归谁**——computer-use 只有一台桌面，用户想知道“现在是谁在用、我还要等多久”。

星桥是唯一能回答这三个问题的**跨会话控制面**。因此首屏不做“功能大全”，只做**决策与异常**：用户打开星桥 5 秒内就能回答“我现在要做什么”，而原生界面永远给不了这个答案。这就是“先看星桥”的产品理由：**它是唯一需要‘巡场’的地方，而巡场应该被压缩成一屏。**

### 10.2 首屏信息层级

| 优先级 | 区块 | 内容 | 空态 |
|---|---|---|---|
| **P0** | 需要你处理 | 待审批（90/92）、加急（85）、卡住（80）、租约等待（82） | “现在没有需要你拍板的事 🎉” + 最近完成 1 条 |
| **P1** | 今日任务流 | 进行中/卡住任务线（按 attention、最近进度排序），每张卡可展开信息流时间线 | “今天还没有任务；发布一个世界任务试试” |
| **P2** | 资源 | computer-use 当前持有者/剩余 TTL/优先级/（4.1 队列） | “桌面空闲” + “谁最适合现在用” |
| **P3（aside/抽屉）** | 在线与空闲、积分/官阶、快捷操作 | 成员 availability、快捷发布/加急/报BUG/找成员 | — |
| **二级页** | 世界 / 群聊 / 任务 / 通知中心 / ⌘K | 现有能力全部保留 | — |

### 10.4 交互规则

- **一跳处理**：P0 卡片上的动作直接发 command（批准/驳回/催办/已处理），成功后本地乐观更新 + 5s 后校正。
- **深链**：所有卡片/条目带 `target`；点击切到对应 tab 并高亮对象（`#/tasks?taskId=…`）。
- **展开而非跳走**：任务卡信息流就地展开（`taskFlows[taskId]`），减少上下文丢失。
- **未读**：顶栏 🔔 数字 = `inbox.unreadCount`；`completion` 未读单独显示 ✅ 完成 badge（现有实现保留）。
- **提示音/弹窗**：只在 `document.visibilityState==='visible' && hasFocus && !fullscreenElement` 时响；其余只加 badge（v3 策略保留）。
- **空态/加载/错误**：P0 空态给出“最近完成”；资源不可用时显示 `degraded` 原因；state 请求失败显示“重连中”而非白屏。
- **移动端 <900px**：单列，P0 → P1 → 资源抽屉；底部 4 tab + FAB（保留 v3 三档响应式）。

## 14. 开放问题（需要 Lead/用户拍板）

1. **多进程并发写 `board.jsonl`/`events.v4.jsonl`**：当前单进程 append 安全；若同时开多个 DSH 实例共享数据目录，需要文件锁或“单写者”约束。建议 4.0 明确“单实例写”，多实例只读。
2. **inbox 未读存放**：`inbox-state.json`（单机一致） vs `localStorage`（多端不一致）。本文选前者；如果做远程访问多端，需要同步策略。
3. **computer-use waiters 暴露**：是否允许改 computer-use 插件写 `waiters.json`？若不允许，4.0 资源页只能显示持有者，不能显示“我排第几”。
4. **审批超时时长**：30min 是否合适？还是按审批类型（招募 30min / 新会话 10min）？
5. **events 保留期**：90 天 + 终态永久，是否满足审计需求？
6. **`board.jsonl` 是否在 4.1 停写**：停写可减一半写放大，但失去旧版本回滚的一半兼容性；建议 4.1 再评估。
